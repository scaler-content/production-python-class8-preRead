2. The big idea: measure before you change

A mechanic who hears a rattle does not start unscrewing parts at random. They listen, they run a test, and only then do they pick up a tool. 5. Measure it, then profile it

“It feels slow” is not a measurement. We want three numbers for every run: how many rows, how many seconds, and how much memory at the peak. time.perf_counter() gives the seconds. Python’s tracemalloc gives the peak memory — but it also slows the code down a lot, so time and memory are always measured in separate runs.

The two small functions you will write in class
def time_it(work):
    start = time.perf_counter()
    result = work()
    return result, time.perf_counter() - start

def peak_memory_mb(work):
    tracemalloc.start()
    result = work()
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return result, peak / 1_000_000

A measurement is only useful once you know where the time goes. A profiler counts that for you. cProfile comes with Python and counts by function; line_profiler (an instructor-only demonstration) counts by line inside one function.

ColumnMeaning
ncallsHow many times the function ran
tottimeTime spent inside the function itself only
cumtimeTime inside the function and everything it calls
A guess the profiler proves wrong Many people suspect that reading a small JSON fixture file for every note is the slow part of a recorded run. In class, cProfile shows that function costs about two percent of the time. The real cost, in live mode, is a suggestion cache that is read from disk and rewritten to disk after every single answer. Profile before you optimise — a reasonable guess is often wrong.

6. One row at a time: iterators and generators

A list holds every item in memory at once. An iterator hands over one item when asked, and says “no more” with StopIteration when it runs out. Most things you already loop over — a list, a csv.DictReader — are iterable. A generator is the easiest way to write your own: a function with yield in it pauses there, and resumes only when the next item is asked for.

A generator pauses at yield
def count_up(limit):
    n = 0
    while n < limit:
        print(f"  (making {n})")
        yield n
        n += 1

g = count_up(3)
print("created, nothing printed yet")
print("got", next(g))   # only now does "(making 0)" print

Chain a few generators together and you get a pipeline where only one item is “in flight” at a time: read a row, parse it, validate it, write it. That is the shape Class 8 gives the Workbench’s intake and output.

7. Four gates before a model call

In live mode, every flagged case with a note is one model call, and at 20,000 rows that is roughly 1,570 calls. A call costs money and time, and the wrong cached answer can be worse than no answer. So Class 8 puts four gates in front of a call, in order, and only the last one costs anything.

1. Eligible?Plain Python: is the note even worth asking about?
→
2. Cached?Do we already have a safe answer for this exact note?
→
3. Budget left?Has this run already used its call cap?
→
4. AskOnly now does a model call happen

There is a real bug behind gate 2. Before Class 8, a cached answer was keyed only by the note’s ID, the model and the prompt version. If the note text itself was edited but kept the same ID, the Workbench silently reused the old, now-wrong answer. The fix is a cache key built from a hash of the whole prompt, so an edited note always asks again.

Cost per usable suggestion, not just cost

A cheaper run is not automatically a better one. If a call cap cuts spend by 90 percent but also leaves most flagged cases with no suggestion at all, “cheaper” is hiding a quality loss. Class 8 computes cost_per_processed_case and cost_per_usable_suggestion, and compares a rule-only approach against the model on the same small eval set, so a lower call count can never quietly hide a worse answer.
